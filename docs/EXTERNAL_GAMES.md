# Private External Games setup and verification

External Games adds a private, no-prize Clash Royale Triple Draft 1v1 workflow. It is disabled by default. The application does not host or automate Clash Royale gameplay. The SOL option is explicitly unavailable and cannot be enabled through an environment flag in this build.

**Single admin setup:** Leave `EXTERNAL_GAMES_TESTER_IDS` blank. Once the provider key, authorized verification and Triple Draft rule are in place, only the existing Arenifi admin can open External Games. Connect the admin's Clash Royale account, agree on a match with an opponent and start **Private practice** with their player tag. The opponent only uses the official game app; they do not receive an Arenifi account or access. Only the admin's ownership is proven in this flow. Both official logs must still agree. Automatic queueing and the two-sided ready check are reserved for deployments with explicitly enabled internal testers.

## Provider access and configuration

1. Confirm the use case is authorized for Arenifi, including the relationship to its existing crypto product. [Supercell's tournament guidelines](https://supercell.com/en/tournament-guidelines/) prohibit player-funded prizes, entry fees, gambling, and certain crypto-related promotion under the published rules. Keep the feature off if the applicable terms or scope of permission are unclear. For exceptions, contact Supercell at the address in those guidelines.
2. Obtain a key in the [Clash Royale Developer Portal](https://developer.clashroyale.com/) for the official HTTPS API. Confirm the permitted API scopes and specifically obtain access to ownership verification before switching `CLASH_ROYALE_VERIFY_TOKEN_ENABLED` on. Permissions for `GET /v1/players/{tag}`, `GET /v1/players/{tag}/battlelog` and `POST /v1/players/{tag}/verifytoken` must be tested with the actual key. A 403 on token verification is not proof of ownership and is not bypassed. No key or authorized account was supplied for live verification.
3. If the developer key requires an IP allowlist, obtain the backend service's actual outbound IPv4 addresses. For Railway, see [Static Outbound IPs](https://docs.railway.com/networking/static-outbound-ips): the service requires Pro for this feature; use **Settings → Networking → Enable Static IPs**, then allowlist every assigned outbound address when configuring the key. The inbound API domain is not the outbound IP. No Railway plan, values or deployment have been changed.
4. In a private staging environment using an isolated MongoDB replica set or Atlas deployment that supports transactions, set `CLASH_ROYALE_API_KEY` as a backend-only secret. Set `EXTERNAL_GAMES_ENABLED=true`, `EXTERNAL_GAMES_ADMIN_ONLY=true`, `CLASH_ROYALE_ENABLED=true`, and `CLASH_ROYALE_VERIFY_TOKEN_ENABLED=true` only after approval. Set `EXTERNAL_GAMES_TESTER_IDS` to the comma-separated Mongo account IDs of the two approved participants. The current Arenifi admin is also permitted; test accounts do not gain admin permissions. Set the flags consistently across all backend replicas. Re-login or allow `/api/me` to refresh, then select **External Games** in the header or open `/external-games`. Ordinary accounts are redirected, and the new API returns 404 for them.

## Validating a live Triple Draft match

1. On **External Games → Connect account**, enter each participant's public Player Tag and check the profile preview. Enter only the API token from in-game settings. Arenifi sends it to the provider and never stores it. Other credentials and public tags are not ownership proof. A confirmed connection is permanently pinned to the Arenifi user; Disconnect only disables it, and re-linking the same tag requires fresh proof. Proof expires for queue entry after 30 days.
2. Before opening the queue, play a known native Triple Draft Friendly Battle outside Arenifi with authorized accounts. Compare the official battle logs for the two views and confirm the type, mode ID, mode name, 1v1 participation and result consistency. An admin can inspect their own sanitized mode metadata under **Internal operations → Load review → Inspect own battle modes**. Compare both perspectives through authorized access to the provider API; the admin tool does not reveal another account's raw logs. Always collect actual evidence; do not use the synthetic tuple in the test or candidate IDs mentioned in earlier discussions.
3. Set `CLASH_ROYALE_TRIPLE_DRAFT_RULE` in the backend to the exact JSON object `{"type": ..., "modeId": ..., "modeName": ...}` observed in the verified records. Without a complete valid tuple, queueing fails closed. Verify the mode is available in the current app before inviting the two testers to queue.
4. Both approved users select **Find Free Play match** and accept within 45 seconds. Wait for both baselines and the server's start time. Use the official in-app Social/Friendly Battle flow, adding each other in the app if necessary. Play exactly one Triple Draft match with the displayed opponent before the 12-minute window closes. Leave Arenifi open or return later to view the verified crown score. A browser disconnect is not a loss.

[Supercell's Quickplay announcement](https://supercell.com/en/games/clashroyale/blog/release-notes/march-update-2026/) documents scanning an in-app QR code for Friendly Battles. It does not document a Triple Draft Quickplay link, a reusable link format, an expiry, or a required host screen for that mode. Its approximately 12-hour note is under Add Friends, not Quickplay. The [Friendly Battles help page](https://support.supercell.com/clash-royale/en/articles/friendly-battles-3.html) describes the native friend/clan path and rotating Special Battles. Triple Draft had official Friendly Battle support [at its introduction](https://supercell.com/en/games/clashroyale/blog/release-notes/the-party-button-update-2/); current availability must still be tested. No invite URL/QR ingestion or undocumented deep links are enabled. Do not substitute another mode if Triple Draft is unavailable.

## Persistence and operational controls

On first enabled use, the backend creates `external_game_links`, `external_game_seats`, `external_game_matches`, `external_game_control`, and `external_game_audit` with their indexes. There is no migration of existing wallet, transaction or account data. The Mongo role needs access to create indexes/collections and use transactions. The link tag and consumed battle fingerprint each have unique indexes. Seat IDs are account IDs, so an account cannot queue or hold two matches. A transaction serializes queue creation, linking, ready checks and terminal updates across replicas. The verification worker leases due matches, with lease expiration permitting recovery after a restart.

Verification requires both logs, an exact provider tuple and participant pair, a server-controlled time window, a result not present in either baseline and consistent scores. The outcome is never provided by the browser. Extra candidates or contradictory scores become disputes rather than letting either party pick a rematch. The worker waits until the window closes plus 2 minutes and requires a current two-sided observation; delayed/missing provider data gets up to 5 more minutes before an expired/disputed outcome. The canonical fingerprint is independent of the provider perspective and crown score. It is not a provider-issued match/session identifier. Two consenting players can still coordinate or intentionally lose; that is not detectable from published scores alone. Repeated pairings are review signals, not automatic sanctions.

Private state updates use authenticated HTTP polling; there is no External Games WebSocket protocol or public subscription. Admin review is separately authorized and exposes states, pending work, only the sanitized evidence kept by the verifier, link history, repeated-pair flags and provider status. **Pause matchmaking** clears active queues and prevents new ready commitments without stopping verification of committed matches. Turning off the environment flags stops the worker as well, so prefer the pause control while matches reconcile. No raw provider token, invite link, in-game login credential or player battle payload is stored.

## SOL custody and launch blockers

The displayed balance is Arenifi's existing balance, not spendable test credits. No SOL reservation, deduction, escrow, payout or refund executes in this build. Setting `CLASH_ROYALE_REAL_STAKES_ENABLED=true` records only the requested configuration in admin status and still rejects all stakes, including requests by admins.

The existing deposit wallets are the custody source of truth. `/api/me` can overwrite the cached Mongo user balance with on-chain RPC data; arena entries and withdrawals can spend from the same wallet. A Mongo-only hold would be bypassed by those paths and would not safely support a $4 payout. Implementing the requested real-balance integration requires written provider permission, applicable compliance approval, and a separately reviewed custody design with integer-lamport locks/escrow and recovery across every signer/spend path. Engineering acceptance requires demonstrating balance conservation, durable handling of partially confirmed reservations, restart reconciliation, idempotent payouts/refunds and non-overlapping spending in an isolated environment. Even with custody solved, do not settle real stakes without provider evidence sufficient to tie the battle to the intended match and rule set. No manual payout path is provided.

## Tests and changed areas

- Backend: `external-games/clash-royale.js`, `external-games/service.js`, `external-games/external-games.test.js`, `server.js`, `.env.example`.
- Frontend: `src/pages/ExternalGames.jsx`, `src/styles/externalGames.css`, `src/App.jsx`, `src/components/AppTopbar.jsx`, `src/utils/seo.js`, `public/_headers`, `scripts/external-games-browser-check.mjs`.
- Run `node --test --test-isolation=none external-games/external-games.test.js` in the backend. The provider and authenticated users are fixtures. Set `EXTERNAL_TEST_MONGO_URI` to a dedicated loopback replica-set URI (`mongodb://127.0.0.1:PORT/?replicaSet=NAME`) for the opt-in Mongo concurrency and restart test. It uses a random disposable database. Never use production credentials or balances.
- Run `npm run build` in the frontend. The browser check exercises ordinary users, revocation at the API, the mobile account/ready flow and the admin review with fixture responses. No live Supercell API key or real Triple Draft match is validated by these tests.
